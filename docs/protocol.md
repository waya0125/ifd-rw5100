# RW-5100 の通信方式

Windows 用の公式ドライバーで RW-5100 を動かし、そのときの USB の通信を Linux の usbmon で記録して読み取った内容です。推測の部分には「たぶん」と書いています。

## USB の構成

| 項目 | 値 |
|------|----|
| USB ID | `04dd:9259` |
| 規格 | USB 1.1、full-speed |
| インターフェース | クラス 255、サブクラス 255、プロトコル 0（メーカー独自） |
| エンドポイント | バルク IN `0x81`、バルク OUT `0x02`（どちらも最大 64 バイト） |
| 割り込みエンドポイント | なし |

公式ドライバーが送るコントロール転送は、記述子の取得（GET_DESCRIPTOR）と設定の選択（SET_CONFIGURATION）だけです。命令はすべてバルク転送で送ります。

割り込みエンドポイントが無いので、カードの抜き挿しは、ホストが状態を問い合わせて知ります（ポーリング）。公式ドライバーは 0.5 秒ごとに問い合わせています。

## 枠の形

どの枠も末尾に XOR のチェックサムが付きます。チェックサムは、枠の先頭からチェックサムの手前までの全バイトの XOR です。

通し番号は 1 往復ごとに `00` と `40` を交互に使います。枠の種類（命令か APDU か）は関係ありません。返事は送った枠と同じ通し番号を返します。

### 命令

ホストから送る枠:

```
12 <通し番号> <長さ> 01 <命令> <データ…> <XOR>
```

リーダーから返る枠:

```
21 <通し番号> <長さ> 01 <命令> <データ…> <状態> 00 <XOR>
```

- `<長さ>` は、`01` からチェックサムの手前までのバイト数です。
- `01` の意味は分かっていません。たぶん宛先かスロットの番号です。
- `<状態>` は、カードに電源が入っている間は `F0`、カードが無いか電源が入っていない間は `F1` でした（たぶん）。

例: 版を聞く命令 `C0` を送ると、`USB Ver1.01` が返ります。

```
送る: 12 00 02 01 C0 D1
返る: 21 00 0F 01 C0 55 53 42 20 56 65 72 31 2E 30 31 F0 00 24
                     U  S  B     V  e  r  1  .  0  1
```

### APDU

カードとのやり取りは、別の形の枠を使います。APDU（CLA から）をそのまま入れます。

```
送る: 52 <通し番号> <長さ> <コマンド APDU> <XOR>
返る: 25 <通し番号> <長さ> <レスポンス APDU（データと SW1 SW2）> <XOR>
```

カードの ATR は T=1 でしたが、ホストは T=1 のブロックを組み立てず、APDU をそのまま送っていました。T=1 の処理はたぶんリーダーの中で行っています。

## 命令の一覧

| 命令 | 送るデータ | 返るデータ | 意味 |
|------|-----------|-----------|------|
| `C0` | なし | 版の文字列（`USB Ver1.01`） | 版を聞く |
| `31` | なし | 1 バイト | カードの状態を聞く。下のビットの組み合わせ |
| `41` | なし | なし | 不明 |
| `D0` | なし | なし | 不明。たぶん初期化 |
| `D1` | `00` または `03` | なし | `00` は電源投入（コールドリセット）、`03` はウォームリセット（たぶん）。返事まで約 0.17〜0.3 秒かかる |
| `35` | `0A 00` | ATR（後ろを `00` で埋めた 36 バイト） | ATR を読む |

## `31` の返事のビット

見えた値は `08`・`20`・`28`・`39` です。ビットの意味は、たぶん次のとおりです。

| ビット | 意味（たぶん） |
|--------|---------------|
| `0x20` | 初期化（`D0`・`41`）が済んだ |
| `0x10` | カードあり |
| `0x08` | 接続直後と、カードを挿す途中で一瞬だけ立つ。意味は分かっていない |
| `0x01` | カードありの時に立つ |

カードがあるかは `0x10` で判定しています。

## 公式ドライバーの手順

接続したとき:

1. `C0`（版）
2. `31`（状態）
3. `D0`、`41` を 2 回くり返す
4. 以後、`31` を 0.5 秒ごとに送る

カードを挿したとき（`31` の返事が `20` から `39` に変わったとき）:

1. `D1 00`（電源を入れる）
2. `35 0A 00`（ATR を読む）

PC/SC の操作に対して公式ドライバーが送ったもの（Windows 7 で `SCardConnect`・`SCardDisconnect`・`SCardReconnect` を呼んで記録）:

| PC/SC の操作 | 送ったもの |
|-------------|-----------|
| `SCardConnect` | `D1 00` → `35 0A 00` |
| `SCardDisconnect(SCARD_UNPOWER_CARD)` | 何も送らない |
| `SCardReconnect(SCARD_UNPOWER_CARD)` | `D1 00` → `35 0A 00` |
| `SCardReconnect(SCARD_RESET_CARD)` | `D1 03` → `35 0A 00` |

公式ドライバーも、カードの電源を切る命令は送りませんでした。

## 分かっていないこと

- `01`、`41`、`D0` の意味
- `35` の `0A 00` の意味
- `D1` の引数の `00`・`03` 以外の値
- カードの電源を切る命令（公式ドライバーも送らないので、無いのかもしれない）
- 64 バイトを超える返事の分け方
- エラーのときの `<状態>` の値

## 気をつけること

### T=0 のカード

T=0 のカード（ATR `3B 0A 41 00 CE 43 00 01 50 1E 01 05`、空の Java カード）で試したところ、次のようになりました。

- このドライバー: `D1 00`・`35 0A 00` で ATR は読めた。APDU（`52` の枠）を送ると返事が来ず、以後 `31` にも返事をしなくなった。カードを抜いても戻らなかった。
- Windows の公式ドライバー: `D1 00` に返事が来ず、約 58 秒後に USB をリセットした。

RW-5100 は、たぶん T=0 のカードに対応していません。

### リーダーが返事をしなくなった時

公式ドライバーは USB をリセットしていました。このドライバーも、返事が来ない時は `libusb_reset_device` で USB をリセットします。リセットすると、リーダーは USB から一度切れて別の番号で出直すので、pcscd が抜き挿しとして扱い、開き直します。

QEMU のパススルーを途中で外した時（`device_del`）は、出直したリーダーの製品名の文字列が正しく返らず、公式ドライバーも開始できませんでした。このときは挿し直すと元に戻りました。
